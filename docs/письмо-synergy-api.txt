Тема: Массовое изменение типа контакта через API — не применяется, запрос молча проходит

Здравствуйте!

Мы пользуемся вашей CRM (account-id 17) и работаем с ней через REST API
https://app.synergycrm.ru/api/v1 по ключу. Чтений и записей много, всё
штатно: заявки, контакты, транспорт, телефония.

Сейчас нам нужно проставить тип контакта примерно 6 200 контактам —
тем, у которых в разделе «Транспорт» есть привязанные карточки техники.
Правило простое: если у контакта есть только техника, ему ставится тип
«Исполнитель»; если есть и техника, и заявки — новый тип «Заказчик/исп.».
Руками это несколько тысяч карточек, поэтому хотим сделать через API.

Проблема: запись типа контакта API принимает, но не применяет.


ЧТО МЫ ПРОБОВАЛИ

Контакт для примера — 3115806 (у него тип не проставлен).

1) Обновление связи внутри ресурса:

   PATCH /api/v1/contacts/3115806
   Content-Type: application/vnd.api+json

   {"data": {"id": "3115806", "type": "contacts",
             "relationships": {"contact-type": {
                 "data": {"type": "contact-types", "id": "101"}}}}}

   Ответ: 200 OK. Последующий GET /api/v1/contacts/3115806 показывает,
   что contact-type по-прежнему пустой. Ошибки нет, изменения тоже нет.

2) Обновление через эндпоинт связи:

   PATCH /api/v1/contacts/3115806/relationships/contact-type

   {"data": {"type": "contact-types", "id": "101"}}

   Ответ: 200 OK, тело пустое. Тип так же не изменился.

3) Попытка передать тип атрибутом:

   PATCH /api/v1/contacts/3115806
   {"data": {"id": "3115806", "type": "contacts",
             "attributes": {"contact-type-id": 101}}}

   Ответ: 400, {"errors":[{"title":"Param not allowed",
   "detail":"contact-type-id is not allowed.","code":"105"}]}

   То же самое с "contact_type_id".

4) Проверка, что запись в контакт вообще работает:

   PATCH /api/v1/contacts/3115806
   {"data": {"id": "3115806", "type": "contacts",
             "attributes": {"position": "проверка записи"}}}

   Ответ: 200 OK, поле «должность» действительно изменилось, затем мы
   вернули прежнее значение. То есть право на запись у ключа есть и
   обычные поля меняются штатно — не применяется именно тип контакта.

Справочник типов при этом читается нормально:
GET /api/v1/contact-types отдаёт 97 «Заказчик», 101 «Исполнитель»,
1138 «Диспетчер», 2055 «Кадры», 4265 «Заказчик/исп.».


ВОПРОСЫ

1. Поддерживается ли изменение типа контакта через API? Если да —
   каким именно запросом и в каком виде передавать значение?

2. Если не поддерживается: есть ли в интерфейсе массовое изменение
   типа у выборки контактов (по списку id, по сегменту, по фильтру)?
   Список id мы подготовим в любом формате.

3. Возможен ли импорт с обновлением существующих контактов по id —
   так, чтобы менялся только тип и не затрагивались остальные поля?

4. Почему при запросе контактов не разрешён фильтр по типу:
   GET /api/v1/contacts?filter[contact-type-id]=101 отвечает
   400 «contact_type_id is not allowed». Как выбрать контакты
   определённого типа через API?

5. Есть ли рекомендованный темп для массовых операций? Сейчас мы
   держим паузу между запросами и корректно обрабатываем 429 с
   Retry-After, но хотим свериться с вашими ограничениями, чтобы
   не мешать работе аккаунта.


ЗАОДНО, ЕСЛИ МОЖНО

Эти фильтры нам тоже не отдаются, а они сильно сократили бы нагрузку
на ваш API с нашей стороны:

- GET /api/v1/transports?filter[contact-id]=...
  400 «contact_id is not allowed» — приходится выгружать все 11 688
  карточек транспорта, чтобы найти технику одного поставщика.

- GET /api/v1/orders?filter[contact-id]=...
  400 «contact_id is not allowed» — по той же причине приходится
  перебирать все 75 282 заявки, чтобы узнать, были ли заявки у
  конкретного контакта.

- Фильтр по дате изменения (updated-at) для заявок, контактов и
  транспорта — чтобы забирать только изменившееся, а не всё целиком.

Если такие фильтры уже есть под другими именами — подскажите, каким
параметром их звать.

И отдельно замечание, которое может быть вам полезно:
GET /api/v1/custom-fields?per_page=50&page[number]=4 стабильно
отвечает 500 Internal Server Error, тогда как соседние страницы
отдаются нормально.

Заранее спасибо. Готовы предоставить любые подробности: номера
запросов, время обращений, примеры контактов.
